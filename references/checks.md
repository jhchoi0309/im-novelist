# 요청에 따른 추가 점검

아래 검사는 사용자가 요청하거나 해당 제한을 알려 준 경우에만 수행한다. 편집·원고 대조·사실 확인·서식 검사 각각의 확인 범위를 구분한다.

## 분량

1. 제한이 글자 수인지 바이트인지, 최대·최소, 공백과 줄바꿈 포함 여부, 제출 시스템의 산정 규칙을 확인한다. 알려지지 않은 기준은 확인 필요로 남기고 임의의 합격 판정을 피한다.
2. 최종 제출할 텍스트 자체를 계산한다. 중간 초안, 설명문, 제목, 문서 서식이나 인용 부호가 제출에 포함되는지 확인한다.
3. 바이트 방식이 문자 인코딩이라면 실제 인코딩으로 계산한다. UTF-8 기준 완성형 한글 한 글자는 보통 3바이트, ASCII는 1바이트지만 결합 문자·이모지·다른 인코딩은 다를 수 있다. 모든 제출처가 UTF-8을 쓴다고 가정하지 않는다.
4. 인코딩, 원문의 줄바꿈 종류와 계산에 적용한 LF·CRLF·원문 유지 방식, 마지막 줄바꿈·공백 포함 여부, 측정값·제한을 결과에 기록한다. 줄바꿈 변환이나 공백 제외는 제출 규칙이 명시한 경우에만 적용한다.
5. 인코딩 기반 바이트 검사에는 설치된 `scripts/count_text.py`를 사용할 수 있다. 도구가 없다면 실행 가능한 실제 계산으로 대체하고, 계산할 수 없으면 그 사실을 밝힌다. 제출처의 자체 글자별 환산 규칙은 이 스크립트로 판정하지 않는다.

예: `python3 scripts/count_text.py 원고.txt --encoding utf-8 --newlines preserve --max-bytes 1000`. 입력은 UTF-8 텍스트 파일이다. `--newlines lf`나 `crlf`는 시스템이 해당 줄바꿈으로 변환하는 경우에만 쓴다. 공백과 마지막 줄바꿈은 항상 포함한다. 입력 파일의 UTF-8 BOM도 문자로 포함하므로 실제 제출 내용과 맞춰야 한다. 본문 자체를 출력하거나 저장·전송하지 않는다.

## 블라인드

1. 사용자가 제공한 공고와 금지 정보·제외 명칭을 기준으로 삼는다. 학교명, 출신지역, 가족관계 등은 해당 기관의 기준에서 금지한 경우에 점검한다. 목록에 없는 기준을 상상하거나 법적 판정으로 단정하지 않는다.
2. 본문뿐 아니라 제공된 표·사진 설명·캡션·머리말과 파일명 등 요청 범위에서 접근 가능한 텍스트도 살핀다. 우회 표현이나 문맥상 식별 가능성은 후보로 설명하고 기계적인 문자열 검색만으로 적합성을 보증하지 않는다.
3. 발견 후보·적용한 기준·확인하지 못한 파일이나 영역을 구분한다. 최종 판정은 채용기관의 공고와 판단에 따른다고 밝힌다. 사용자가 지정한 명칭을 삭제할 때도 사실관계나 문장 의미를 새로 만들지 않는다.

## 사실·프로젝트 검증

원고의 전후 대조는 사실 여부나 실제 코드 동작을 입증하지 않는다. 사용자가 별도 검증을 요청하면 이용 가능한 원자료·코드·실행 결과를 확인하고 확인한 근거, 상충 내용, 접근 불가·미검증 항목을 구분한다. 날짜 누락 시 연속 판정 같은 구현 질문은 구현이나 재현 가능한 검증 없이 원고만으로 확인됐다고 말하지 않는다.

## 최종 배치

문서 파일 편집이나 배치 검사 요청이 있을 때 적용한다. 편집 전과 후의 최종 파일을 가능한 방식으로 렌더링해 페이지별로 다음을 살핀다.

- 사진 누락·잘림·순서·비율, 사진과 설명의 연결.
- 표의 잘린 행·열·숫자, 쪽 나눔과 반복 머리글, 표와 캡션의 관계.
- 제목·문단·캡션의 고립, 겹침, 빈 페이지, 여백과 페이지 나눔.
- 편집하지 않기로 한 인용·수치·사진과 본문의 보존.

문서의 텍스트 추출이나 원본 파일 존재만으로 시각적 배치가 확인됐다고 하지 않는다. 렌더링이나 시각 확인이 불가능하면 무엇을 확인하지 못했는지 보고한다.
